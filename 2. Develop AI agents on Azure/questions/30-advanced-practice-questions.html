2.1 Develop AI Agents with Foundry and VS Code

4 questions

1. Managed instructions or a custom runtime?

A team already has a working containerized agent with custom orchestration and a specialized runtime dependency. It must retain this implementation rather than express everything as instructions and supported built-in tools. The target environment supports Foundry hosted agents, and the team wants managed hosting and scaling rather than running its own servers.

Which deployment approach best fits?

  1. Convert the application into a prompt-only agent without retaining its runtime code.
  2. Package the custom runtime as a hosted agent using the supported Foundry hosting contract.
  3. Upload the container source files to File Search and ask a prompt agent to execute them.
  4. Expose only the underlying model deployment and assume its endpoint will run the custom orchestration.
Answer

Answer: B

Why: Hosted agents address custom runtime code with managed hosting. The requirement is not merely choosing a model or adding instructions.

  • A: Discards the explicitly required implementation.
  • C: File retrieval does not host an application runtime.
  • D: A model inference endpoint does not execute arbitrary application orchestration.

Validate the container's supported contract, dependencies, tool access, and operational limits; managed hosting does not grant unrestricted execution permissions.

2. Portal and VS Code tests disagree

A support agent passes tests in the Foundry portal but calls the wrong tool when invoked by a VS Code application. Both clients authenticate successfully. Traces show that the application resolves a different project and an older agent configuration with different tool instructions. The team must make test results reproducible before changing the model.

What should it do first?

  1. Increase temperature in both clients to make their behavior more similar.
  2. Grant subscription-wide roles to the developer identity.
  3. Retrain the model using the portal's successful answers.
  4. Align the project, agent version/configuration, model deployment, and tool connections; rerun identical cases and compare traces.
Answer

Answer: D

Why: The evidence establishes configuration drift. Compare the same agent under the same inputs before diagnosing probabilistic model behavior.

  • A: Changes generation behavior without fixing the different configurations.
  • B: Authentication works; broad roles neither align versions nor fix tool instructions.
  • C: Adds training cost before addressing the proven deployment mismatch.

Record the effective configuration and deployment identifiers in safe diagnostics, not secrets or raw customer content.

3. Conversation continuity without cross-user memory

A web application uses one server-side agent definition for all customers. To preserve history, it also reuses a single conversation identifier for everyone. One customer's response includes facts from a previous customer's interaction. The product needs continuity within each user's conversation but must isolate different users.

Which design should replace the current state handling?

  1. Bind separate conversation/session state to the authenticated user and conversation, authorize access on every request, and apply retention controls.
  2. Keep the shared conversation and append the current customer's name to the latest prompt.
  3. Hide conversation identifiers in the browser while continuing to reuse one server-side history.
  4. Create a separate model deployment per customer but keep the shared conversation history.
Answer

Answer: A

Why: An agent definition can be shared, but interaction state must be scoped and access-controlled. Names in prompts do not isolate stored history.

  • B: Restricted content remains available to the model.
  • C: Concealing an identifier is not authorization or state isolation.
  • D: Model deployment separation does not fix shared input history.

4. A correct answer can hide the wrong actions

A refund agent's final messages score well on relevance and groundedness. Run traces nevertheless show that it sometimes issues the same refund twice or queries an unrelated account before giving the correct answer. The release gate must assess actual behavior, not just the prose.

Choose TWO additions to the evaluation plan.

  1. Use final-answer fluency as a replacement for examining backend effects.
  2. Evaluate tool trajectories, arguments, authorization decisions, and resulting backend effects against expected outcomes.
  3. Increase the output-token limit and assume more explanation indicates better behavior.
  4. Include denied-access, timeout, retry, and approval scenarios; correlate results with privacy-controlled model/tool traces.
  5. Remove failing traces if the final response remains correct.
Answer

Answer: B, D

Why: Agent quality includes permitted actions and their effects. Failure-path tests expose behavior that answer-only metrics miss.

  • A: Fluent prose says nothing about unauthorized reads or duplicate writes.
  • C: A longer explanation does not constrain execution.
  • E: Hides a release-blocking failure rather than measuring it.

Use controlled test backends or fixtures for consequential actions. Do not issue real refunds merely to evaluate an agent.

2.2 Integrate Custom Tools into Your Agent

5 questions

Case study for Q5-9: A retailer's agent uses a maintained Azure AI Search index for current policies. The application owns authenticated order functions and must validate and execute write operations itself. Cancellations use an API supporting operation identifiers, status lookup, and deduplication. Authorization is enforced independently of model decisions; designated high-risk actions require approval.

5. Combine computation with current evidence

An authorized analyst uploads a CSV of completed orders. They ask for exact monthly aggregates, a chart, and an explanation using current warranty policy. No live order action is needed. The team wants managed sandboxed computation and must reuse the existing policy index rather than create another copy.

Which tool combination should you select?

  1. File Search for the CSV and policies, asking the model to sum only the retrieved rows.
  2. Code Interpreter alone, relying on its model's training data for the latest policy.
  3. Code Interpreter for calculations/charting plus authorized Azure AI Search retrieval for current policy evidence.
  4. An order-cancellation function plus a prompt requesting a chart.
Answer

Answer: C

Why: Sandbox computation and evidence retrieval solve distinct requirements. Keep interpreter inputs tenant-scoped and policy retrieval authorized.

  • A: Retrieved fragments are not necessarily the full dataset needed for correct aggregates; it also duplicates the policy store.
  • B: Does not supply the current private policy.
  • D: Exposes an unnecessary write action and does not provide the required computation capability.

6. Ordering: application-executed tool calls

The agent requests a cancellation using function calling. The application must validate the requested arguments and approval before any write, then return the correlated result so the agent can continue.

  1. Validate concrete arguments, caller permissions, and required approval.
  2. Submit the tool result with the original call identifier and continue generation.
  3. Send the user request and available tool schemas to the model.
  4. Execute the permitted operation and capture an authoritative result or explicit error.
  5. Receive the model's requested tool name, arguments, and call identifier.

Which sequence is correct?

  1. 3 → 5 → 4 → 1 → 2
  2. 3 → 5 → 1 → 4 → 2
  3. 1 → 3 → 5 → 4 → 2
  4. 3 → 5 → 1 → 2 → 4
Answer

Answer: B

Why: Describe the tool, receive the request, validate it, execute only if permitted, and return the matching result. Rejected calls take an explicit denied/error path without performing the write.

  • A: Checks authorization after the side effect.
  • C: Validates concrete requested arguments before receiving them; static permission setup is not that validation.
  • D: Returns a result before the operation produces it.

7. The timeout did not necessarily cancel the action

An authorized cancellation reaches the backend, but the connection times out before its response arrives. The agent wants to retry. The API may already have committed the cancellation and emitted a downstream event.

Which execution policy best prevents duplicate effects while reporting the truth?

  1. Use a new operation identifier for every retry so the backend treats each attempt independently.
  2. Tell the agent the cancellation succeeded to prevent another call.
  3. Retry indefinitely because a timeout proves that no server-side work completed.
  4. Preserve the operation identifier, check authoritative status, and retry through the idempotent API only as appropriate; surface unresolved outcomes explicitly.
Answer

Answer: D

Why: An unknown outcome differs from a failed operation. Backend-supported idempotency and status checks are stronger than asking the model not to duplicate actions.

  • A: Defeats deduplication.
  • B: Fabricates success.
  • C: Misinterprets a transport failure and creates unbounded risk.

An identifier alone provides no guarantee unless the backend actually enforces idempotency.

8. Select integration by execution ownership

The retailer adds a read-only supplier inventory API with a compatible OpenAPI specification and supported authentication. Its cancellation logic remains in an existing application-owned function; security requires that application to execute cancellations. The team wants to avoid unnecessary adapters.

Choose TWO integrations, one for each requirement.

  1. Use an OpenAPI tool for the supplier's supported inventory operations.
  2. Upload the supplier specification to File Search and treat descriptions as live inventory results.
  3. Use function calling for cancellations, with validation, approval, and execution in the application.
  4. Replace the cancellation executor with a model-generated success message.
  5. Build a new MCP server for both systems solely to avoid using two supported integration mechanisms.
Answer

Answer: A, C

Why: OpenAPI reuses an existing service contract; function calling retains execution ownership where required.

  • B: Documentation is not the live inventory endpoint.
  • D: Produces text rather than performing the authorized transaction.
  • E: Adds an unnecessary adapter and does not itself resolve execution or authorization requirements.

9. A valid tool schema is not authorization

The cancellation function accepts a correctly formatted order identifier and reason. A user supplies another customer's valid identifier, which passes schema validation. The agent says the user confirmed ownership. The backend has authoritative order-to-account records.

Which control must decide whether the tool can execute?

  1. A backend ownership/permission check using trusted caller identity and authoritative order data.
  2. The model's statement that the user confirmed ownership.
  3. A longer description in the tool schema saying "only cancel your own orders."
  4. The fact that the identifier matches the expected data type and pattern.
Answer

Answer: A

Why: A syntactically valid request can still be unauthorized. Schema validation, tool selection, and business authorization are distinct.

  • B: Trusts a generated interpretation rather than authoritative identity and ownership.
  • C: Guides selection but is not an access-control boundary.
  • D: Proves only structural validity.

Human approval cannot grant permissions the approver does not possess.

10. A local MCP command is not a cloud endpoint

A developer uses an MCP server launched by a local command in VS Code. A cloud-hosted Foundry agent must use the same capability after the laptop is shut down. The selected Foundry integration expects a reachable remote MCP endpoint, and the service supports a remote deployment mode.

Which change should the team make?

  1. Paste the laptop's local launch command into the agent's instructions.
  2. Use the laptop's localhost address as the cloud agent's server address.
  3. Host the server using a supported remote MCP transport, configure network reachability and authentication, and connect the agent to that endpoint.
  4. Upload the local MCP configuration file as knowledge and expect Foundry to host the process automatically.
Answer

Answer: C

Why: MCP standardizes an interface, not automatic process hosting or connectivity. The calling runtime determines which transport and endpoint are reachable.

  • A: Instructions do not provision a remote process.
  • B: Localhost refers to the caller's environment, not the developer's laptop.
  • D: Retrieved configuration is not deployment infrastructure.

11. Approval must match the action that executes

An MCP tool can submit purchase orders. A user approves an order for 20 items, but the agent subsequently changes the arguments to 200 items. The system currently remembers only that "this conversation has approval." Backend authorization allows both quantities, but company policy requires approval of the actual purchase.

Which approval design meets the requirement?

  1. Reuse the conversation-level approval because the tool name did not change.
  2. Bind approval to the concrete operation and material arguments; require renewed approval after material changes, then revalidate before execution.
  3. Ask the model whether the quantity change is important enough to mention, without enforcing the result.
  4. Disable approvals because successful authentication already permits the tool connection.
Answer

Answer: B

Why: Consent for one operation is not consent for a different one. Preserve an auditable association between approved data and the executed action.

  • A: Grants broader authority than the user approved.
  • C: Leaves a mandatory control to an unenforced model judgment.
  • D: Confuses authentication with business approval.

12. Tool discovery does not imply tool trust

A remote MCP server exposes read-only search and administrative write tools. A research agent needs only search. Tool results may contain third-party text, including instructions to call administrative tools. The team must limit capability and prevent returned content from redefining agent authority.

Choose TWO controls.

  1. Expose only required tools and configure least-privilege server-side credentials/authorization.
  2. Expose all tools and depend on their descriptions to discourage writes.
  3. Treat every MCP tool result as a trusted system instruction because the protocol is standardized.
  4. Treat results as untrusted data, apply appropriate injection defenses, and independently enforce permissions and approval on subsequent actions.
  5. Remove source metadata from results so the agent cannot notice where hostile text originated.
Answer

Answer: A, D

Why: Restrict the available operations and the authority of the backend identity; preserve the boundary between retrieved content and executable instructions.

  • B: Tool descriptions are not an authorization mechanism.
  • C: A protocol does not make arbitrary payloads trustworthy.
  • E: Removes useful provenance without limiting attacks.

13. Share a knowledge platform, not stale copies

Three departmental agents need the same approved policy sources, updated daily. Each currently maintains a separate upload store, causing inconsistent answers and duplicate ingestion work. The team wants a reusable knowledge platform and consistent citation behavior, while preserving access restrictions.

Which design should it adopt?

  1. Fine-tune each agent daily and remove all retrieval.
  2. Copy one agent's entire conversation history to the other agents as their knowledge base.
  3. Publish all source documents anonymously so every agent can retrieve the same content.
  4. Configure shared Foundry IQ knowledge bases over appropriate sources, connect each agent with correct access configuration, and define/test retrieval and citation instructions.
Answer

Answer: D

Why: A shared knowledge layer avoids agent-specific copies while keeping retrieval, provenance, and access management explicit.

  • A: Repeated training is not a substitute for current source retrieval.
  • B: Conversation memory mixes interaction state with enterprise knowledge and can leak data.
  • C: Eliminates required access restrictions.

Shared infrastructure does not mean every agent or user receives identical access. Validate source-specific permission behavior.

14. A citation can be genuine and still support the wrong answer

A knowledge-connected agent consistently cites a real policy page. The page has been superseded, but both versions remain retrievable without effective-date metadata. The agent retrieves successfully and faithfully summarizes the older page. Product policy requires current answers unless the user explicitly asks about history.

Which correction targets the root cause?

  1. Maintain version/effective-date metadata and freshness rules, distinguish current from historical retrieval, and verify that citations support the selected policy version.
  2. Increase the agent's confidence wording because the citation is valid.
  3. Evaluate only whether each answer contains at least one clickable link.
  4. Disable retrieval and use the model's prior knowledge for current policy.
Answer

Answer: A

Why: Citation presence and groundedness do not prove temporal correctness. Retrieval must select evidence appropriate to the user's date requirement.

  • B: Makes a stale answer sound more certain.
  • C: Measures link presence rather than source validity and relevance.
  • D: Removes the reliable mechanism for accessing current private policy.

15. Correct knowledge-base access requires both identity and boundaries

An agent must answer from HR material according to the requesting user's permissions. Its retrieval integration can enforce the required permission scope, but the application currently substitutes a broad administrator connection and caches responses by question text alone. Access membership changes over time.

Choose TWO changes that address both exposure paths.

  1. Keep the administrator connection and tell the agent not to mention restricted records.
  2. Use the supported identity/permission propagation or trusted backend enforcement so retrieval returns only material authorized for the caller.
  3. Reuse cached answers across users but hide document titles.
  4. Assume any product called a knowledge base automatically fixes the application's administrator connection.
  5. Scope cache reuse to authorization and source validity; invalidate or revalidate when permissions or content change.
Answer

Answer: B, E

Why: Live retrieval and cached answers are separate data-delivery paths. Both must honor the caller's current access and the source's validity.

  • A: Restricted content already reaches the model.
  • C: A title-free answer can still disclose sensitive facts.
  • D: Ignores the explicitly misconfigured identity boundary.

4 questions

Case study for Q19-22: An invoice workflow extracts fields, validates them against authoritative records, routes exceptions for human review, and writes approved results to an accounting API. Every invoice must produce a traceable outcome. Missing, invalid, or uncertain outputs must not silently become approved invoices.

19. Route by a validated value, not narrative text

The extraction agent writes a free-text recommendation such as "approved except for a possible duplicate." A condition checks whether the text contains "approved," causing some exceptions to enter the payment branch. The workflow supports structured outputs, variables, and conditional nodes.

Which replacement is most reliable?

  1. Check whether the word "approved" occurs twice.
  2. Ask the agent to use more confident wording for valid invoices.
  3. Route according to response length because exceptions tend to be longer.
  4. Use a validated structured status/required fields, map them into workflow variables, and branch explicitly with a safe invalid/unknown path.
Answer

Answer: D

Why: Workflow routing needs a defined data contract and explicit error handling, not a fragile substring test over prose.

  • A: Repeats the same ambiguity rather than eliminating it.
  • B: Confidence language is not validation.
  • C: Uses an unrelated statistical proxy for a business decision.

Structured status is still a model output; business authorization and authoritative checks remain separate.

20. Partial batch failure without invisible missing invoices

A request contains 25 independent invoices. Two extraction calls fail; the others can proceed to validation. The user requires a result for every input invoice, preserving its identifier, and does not want the successful invoices rerun unnecessarily. The workflow supports For-Each processing and explicit failure branches.

Which design should you use?

  1. Process with For-Each and per-item validation/error paths; aggregate one identified success, review, or failure outcome per invoice.
  2. Discard the two failed items and report that the batch completed successfully.
  3. Retry all 25 indefinitely until every extraction returns text.
  4. Combine all outputs into one unkeyed paragraph so missing results are not visible.
Answer

Answer: A

Why: Independent processing plus explicit per-item outcomes allows partial progress without losing completeness or traceability.

  • B: Violates the required outcome for every input.
  • C: Repeats successful work and has no termination guarantee.
  • D: Removes the identifier-to-result association needed for audit and retry.

Apply bounded retries where appropriate and preserve operation identifiers for any downstream writes.

21. Human approval is stale after a material change

An invoice waits for human approval overnight. Before the workflow resumes, a correction changes its amount and destination account. The workflow stores the original approval but does not record which invoice version was approved.

Which design prevents approval from being applied to the changed invoice?

  1. Store only an approved Boolean on the customer account for reuse by all invoices.
  2. Resume directly into payment because a human previously approved something in the workflow.
  3. Bind approval to the invoice version and material fields, revalidate on resume, and request new approval when those fields change.
  4. Ask the model whether the new destination account looks similar to the old one.
Answer

Answer: C

Why: Approval must identify the state and operation being approved. Resumption is a point to recheck stale assumptions and current authorization.

  • A: Broadens approval far beyond a specific invoice.
  • B: Executes a different transaction from the one approved.
  • D: Replaces a deterministic policy check with a guess.

22. Power Fx: every condition is mandatory

Within a Power Fx condition, local workflow variables have already been validated: Local.Amount is numeric and the other variables are Boolean. An invoice can proceed automatically only when its amount is at most 500, its account is verified, and no duplicate is flagged. All other invoices require review. Use the locale syntax shown in the options.

Which condition implements the rule?

  1. Or(Local.Amount <= 500, Local.AccountVerified, Not(Local.DuplicateFlag))
  2. And(Local.Amount <= 500, Local.AccountVerified, Not(Local.DuplicateFlag))
  3. And(Local.Amount < 500, Local.AccountVerified, Not(Local.DuplicateFlag))
  4. And(Local.Amount <= 500, Local.AccountVerified, Local.DuplicateFlag)
Answer

Answer: B

Why: All three requirements must be true; the amount limit includes exactly 500, and duplicate status must be false.

  • A: Allows one passing condition to override failed requirements.
  • C: Incorrectly excludes an otherwise valid amount of exactly 500.
  • D: Requires a duplicate rather than excluding one.

Invalid or missing fields must take the explicit review/error path before this condition, not default to permissive values.

24. Recover a conversation after application restart

Which state design should you use?

Apply retention, concurrency controls, and deletion requirements to persisted history as well as current requests.

25. Registered plugin function returns a misleading default

Why: Business data and execution failures need distinct representations. A successful-looking fallback lets the agent make a false factual claim.

  • A: Invents inventory.

2.8 Orchestrate Multiple Agents with Agent Framework

3 questions

26. Parallelize only independent work

A proposal workflow extracts structured requirements in 3 seconds. Cost analysis takes 6 seconds and security analysis takes 9 seconds; both need the extraction output but neither needs the other's result. A final drafting agent takes 4 seconds and must receive both analyses. Ignore orchestration overhead and assume sufficient capacity.

Which design meets every dependency with the lowest ideal elapsed time?

  1. Run all four stages sequentially: 22 seconds.
  2. Extract, run both analyses concurrently, join, then draft: 16 seconds.
  3. Start every stage concurrently: 9 seconds.
  4. Extract, use only the faster analysis, then draft: 13 seconds.
Answer

Answer: B

Why: The critical path is 3 + max(6, 9) + 4 = 16 seconds. Fan-out/fan-in reduces elapsed time without discarding dependencies.

  • A: Correct but slower.
  • C: Starts consumers before their inputs exist.
  • D: Omits the mandatory security analysis.

Production latency also includes orchestration, rate limiting, and retries; concurrency is not unlimited capacity.

27. A reviewer loop that never concludes

A group-chat solution has a writer and reviewer. The reviewer repeatedly requests stylistic changes after the substantive requirements have been met. Each call stays within its output-token limit, but the group continues indefinitely. The team needs useful feedback and guaranteed termination with an honest outcome.

Choose TWO orchestration controls.

  1. Define explicit acceptance/termination criteria and a clear rule for which agent or controller determines completion.
  2. Increase the context window so the revision history can grow without interruption.
  3. Lower per-call output tokens and assume that bounds the number of calls.
  4. Declare success whenever the last reviewer message is short, regardless of its content.
  5. Enforce a workflow-wide iteration/time/token budget with an explicit incomplete or human-review outcome when exhausted.
Answer

Answer: A, E

Why: Criteria define successful completion; budgets guarantee termination when the agents fail to reach it.

  • B: Retains more history without controlling the loop.
  • C: Bounds one call, not the total workflow.
  • D: Substitutes a weak proxy for task completion.

Selection policies decide who acts next; termination policies decide whether another turn is allowed. Neither replaces the other.

28. Transfer control rather than ask every specialist

A customer-support conversation begins with a triage agent. Based on the issue, one specialist should take over, ask follow-up questions, and possibly transfer to another specialist. Running every specialist for every message would expose unnecessary context and add cost. The next specialist is not known in advance.

Which orchestration pattern best fits?

  1. A fixed sequential pipeline that invokes every specialist in the same order.
  2. Concurrent fan-out to every specialist followed by aggregation on every turn.
  3. A group chat requiring every specialist to comment before each user response.
  4. Handoff orchestration with permitted transfer paths, scoped context, and explicit completion/escalation rules.
Answer

Answer: D

Why: The scenario requires dynamic transfer of conversational responsibility, not a mandatory pipeline or all-agent consensus.

  • A: Assumes a fixed sequence and unnecessary participation.
  • B: Runs independent analyses even though the user needs a responsible specialist.
  • C: Adds broad participation and context exposure contrary to the requirement.

A handoff must not silently broaden the receiving agent's permissions or copy more history than needed.

29. A remote agent is not merely a function schema

A partner operates an autonomous specialist agent on a different platform. It already exposes an A2A endpoint, an Agent Card, and task-status handling. Your orchestrator must discover the specialist's skills and supported interaction modes, delegate a task, and track its outcome without replacing the partner's internal runtime.

Which integration should you select?

  1. An A2A client that retrieves and validates the Agent Card, authenticates as required, and interacts with the remote agent's supported task interface.
  2. An MCP client pointed at the A2A endpoint, assuming all agent/tool protocols are interchangeable.
  3. File Search over a copy of the partner's Agent Card as a substitute for invoking the live agent.
  4. A local prompt containing the partner's name, with no remote interaction.
Answer

Answer: A

Why: Reuse the advertised A2A contract for agent discovery and collaboration, including capabilities, authentication requirements, and task handling.

  • B: MCP and A2A are distinct protocols; one endpoint is not automatically compatible with both.
  • C: Retrieves a description but never delegates a task.
  • D: Simulates a role locally instead of using the required remote specialist.

An Agent Card advertises capabilities; it is not proof of trustworthiness or an authorization grant. MCP can also expose agent-backed tools, but this scenario explicitly provides A2A.

30. Ordering: accepted is not completed

A remote A2A specialist accepts a long-running task. It can request additional input or finish with a result, failure, or cancellation. Your application must use its supported discovery/task capabilities and must not report a successful business outcome just because the request was accepted.

  1. Submit the delegated task through the authenticated, supported interaction.
  2. Validate the terminal outcome and required artifact/result; return success only when the completion contract is satisfied.
  3. Retrieve and validate the trusted agent's card, skills, interaction capabilities, and authentication requirements.
  4. Track the returned task using supported status/streaming mechanisms, handle input requests, and apply bounded waiting/cancellation policy.
  5. Establish the required authenticated client connection and confirm that the intended task is permitted.

Which sequence is correct?

  1. 3 → 5 → 1 → 2 → 4
  2. 1 → 3 → 5 → 4 → 2
  3. 3 → 5 → 1 → 4 → 2
  4. 3 → 1 → 4 → 2 → 5
Answer

Answer: C

Why: Discover the contract, establish permitted access, delegate, observe progress, and validate the terminal result. Apply any required authentication to discovery itself as well.

  • A: Treats acceptance as enough to validate completion before tracking progress.
  • B: Submits before understanding the supported interface or establishing the required access.
  • D: Defers authorization until after the task and result handling.

Honor the protocol/version's actual states and advertised capabilities. A timeout or cancellation request is not proof that all remote effects have stopped.
